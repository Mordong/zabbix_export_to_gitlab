# DR-Recovery — восстановление Zabbix из выгрузок GitLab

Runbook по восстановлению конфигурации Zabbix 7.4 из YAML-выгрузок, которые
формирует `zabbix_export_to_gitlab` (Airflow DAG → GitLab). Документ
рассчитан на чтение в аварийной ситуации — действуйте по шагам сверху вниз.

> **Версия инструмента:** актуально для экспорта ≥ v1.7.0.
> **Окружения:** примеры даны для `prod`; для `test` замените суффикс.

---

## 0. Что эти выгрузки восстанавливают, а что — нет

Это критично понять до начала, иначе ожидания разойдутся с реальностью.

**Восстанавливается из git (конфигурация):**
- шаблоны (`templates/`);
- аутентификация и provisioning LDAP/SAML (`auth/`);
- роли, группы пользователей с правами, локальные пользователи (`users/`);
- типы оповещений и действия (`alerting/`);
- группы хостов/шаблонов, глобальные макросы, хосты (`core/`);
- прокси, прокси-группы, сетевое обнаружение, обслуживание (`infra/` и корень);
- карты, дашборды, скрипты (`maps/`, `dashboards/`, `scripts/`).

**НЕ восстанавливается из git (требует отдельных источников):**
- **Секреты.** Пароли локальных пользователей, секретные макросы, TLS PSK
  прокси, токены вебхуков и пароли скриптов в выгрузках помечены `[SECRET]`
  или отсутствуют. Их нужно ввести вручную из защищённого хранилища — см.
  раздел 6.
- **Исторические данные метрик** (history/trends). Это содержимое БД Zabbix,
  а не конфигурация. Восстанавливается только из бэкапа БД — см. раздел 7.
- **Состояние среды выполнения:** активные проблемы, подтверждения, сессии,
  токены API — не являются частью конфигурации и не переносятся.

## 1. Предварительные требования

Перед началом убедитесь, что в наличии:

- Развёрнутый и работающий **Zabbix server 7.4.5** и веб-интерфейс (сам
  бинарный сервер, БД-движок и веб ставятся штатно, до импорта конфигурации).
- Доступ к репозиторию GitLab с выгрузками (проект ID `2246`); определите
  ветку и коммит, **на который восстанавливаетесь** (обычно `main`, последний
  «зелёный» прогон; при порче — коммит до инцидента).
- Учётная запись Zabbix с ролью **Super admin** (импорт конфигурации и
  создание пользователей требуют максимальных прав).
- Доступ к **хранилищу секретов** (раздел 6) — без него часть объектов
  поднимется без рабочих паролей/PSK/токенов.
- Если планируется восстановление метрик — **бэкап БД** (раздел 7).

Выберите момент времени для восстановления:

```bash
git clone <repo-url> zabbix-config
cd zabbix-config
git checkout <branch-or-commit>   # например: main, или коммит до инцидента
```

## 2. Порядок импорта (КРИТИЧНО)

Объекты Zabbix ссылаются друг на друга по ID/именам. Импорт в неправильном
порядке приведёт к ошибкам «не найдена группа/роль/шаблон». Соблюдайте
последовательность — каждый следующий слой опирается на предыдущий:

1. **Группы** — группы хостов и шаблонов (`core/hostgroups.yaml`,
   `core/templategroups.yaml`). На них держатся права и привязки.
2. **Шаблоны** (`templates/`). Ссылаются на группы шаблонов.
3. **Глобальные макросы** (`core/macros.yaml`). Нужны шаблонам/хостам для
   подстановок (секретные — см. раздел 6).
4. **Роли → группы пользователей → пользователи**
   (`users/roles.yaml` → `users/usergroups.yaml` → `users/users.yaml`).
   Строго в этом порядке: группы ссылаются на роли, пользователи — на роли и
   группы. Это же — фундамент для LDAP-provisioning.
5. **Аутентификация и provisioning** (`auth/authentication.yaml`,
   `auth/userdirectories.yaml`). После ролей/групп — provisioning-маппинг
   ссылается на их ID.
6. **Типы оповещений → действия** (`alerting/mediatypes.yaml` →
   `alerting/actions.yaml`). Действия ссылаются на типы оповещений и группы.
7. **Прокси и прокси-группы** (`infra/proxies/*`, `proxygroups.yaml`). До
   хостов, если хосты опрашиваются через прокси.
8. **Хосты** (`core/hosts/*.yaml`). Ссылаются на группы, шаблоны, прокси,
   макросы — поэтому идут после них.
9. **Сетевое обнаружение, обслуживание** (`drules.yaml`,
   `maintenance.yaml`). Ссылаются на группы/прокси.
10. **Карты, дашборды, скрипты** (`maps/`, `dashboards/`, `scripts/`).
    Ссылаются на хосты/группы — поэтому в самом конце.

> Если восстанавливаете не всё, а часть — всё равно соблюдайте относительный
> порядок зависимостей между затронутыми слоями.

## 3. Путь А — импорт через веб-интерфейс (Configuration import)

Подходит для частичного восстановления и небольших объёмов. Для тысяч хостов
используйте Путь Б (раздел 4).

Для каждого файла в порядке из раздела 2:

1. В веб-интерфейсе откройте раздел импорта конфигурации
   (Data collection / Users / Alerts — в зависимости от типа объекта;
   в 7.4 импорт доступен из соответствующих разделов и из
   **Configuration import**, где это поддерживается).
2. Выберите YAML-файл из локального клона репозитория.
3. В диалоге импорта отметьте правила: **Create new** и **Update existing**.
   Для первичного восстановления с нуля достаточно Create new; для отката
   части объектов включите и Update existing. **Delete missing** включайте
   осознанно — оно удаляет объекты, которых нет в файле.
4. Нажмите Import, проверьте сводку (создано/обновлено) и отсутствие ошибок.
5. Переходите к следующему файлу строго по порядку зависимостей.

Объекты, которые экспортированы как `*.get` (не configuration.export) —
`roles.yaml`, `usergroups.yaml`, `users.yaml`, `actions.yaml`,
`macros.yaml`, `auth/*`, `proxygroups.yaml`, `drules.yaml`,
`maintenance.yaml`, `dashboards/*`, `scripts/*` — **веб-импорт
configuration.import не принимает**. Их восстанавливают через API
(Путь Б) или, при малом числе, вручную через UI по содержимому YAML как
референсу. Через configuration.import (UI и API) импортируются: шаблоны,
группы хостов/шаблонов, хосты, media types, карты.

## 4. Путь Б — импорт через API (configuration.import + *.create)

Подходит для полного восстановления и больших объёмов (тысячи хостов).

### 4.1. Объекты формата configuration.export

Файлы `core/hostgroups.yaml`, `core/templategroups.yaml`, `templates/*`,
`core/hosts/*.yaml`, `alerting/mediatypes.yaml`, `maps/*` импортируются
методом `configuration.import`. Каркас скрипта (Python, stdlib + PyYAML):

```python
import json, urllib.request

ZBX = "https://zabbix.example.com/api_jsonrpc.php"
TOKEN = "<super-admin-api-token>"   # из хранилища секретов

def call(method, params):
    req = urllib.request.Request(
        ZBX,
        data=json.dumps({"jsonrpc": "2.0", "method": method,
                         "params": params, "id": 1}).encode(),
        headers={"Content-Type": "application/json-rpc",
                 "Authorization": f"Bearer {TOKEN}"},
    )
    resp = json.loads(urllib.request.urlopen(req).read())
    if "error" in resp:
        raise RuntimeError(resp["error"])
    return resp["result"]

def import_yaml(path):
    with open(path, encoding="utf-8") as f:
        source = f.read()
    call("configuration.import", {
        "format": "yaml",
        "rules": {
            # Включайте createMissing/updateExisting по сценарию.
            "host_groups":     {"createMissing": True, "updateExisting": True},
            "template_groups": {"createMissing": True, "updateExisting": True},
            "templates":       {"createMissing": True, "updateExisting": True},
            "hosts":           {"createMissing": True, "updateExisting": True},
            "valueMaps":       {"createMissing": True, "updateExisting": True},
            "mediaTypes":      {"createMissing": True, "updateExisting": True},
            "maps":            {"createMissing": True, "updateExisting": True},
        },
        "source": source,
    })
```

Импортируйте по порядку из раздела 2. Хосты лежат по одному файлу в
`core/hosts/<имя>_<hostid>.yaml` — обходите каталог и импортируйте каждый
(hostid в имени — только для уникальности файла, на импорт не влияет).

> **Delete missing для хостов.** Если восстанавливаете «эталон» поверх
> загрязнённой инсталляции и нужно удалить лишние хосты, включите
> `"hosts": {..., "deleteMissing": True}` — но **только** при полном наборе
> файлов, иначе удалите живое.

### 4.2. Объекты формата *.get (восстановление через *.create)

`roles.yaml`, `usergroups.yaml`, `users.yaml`, `actions.yaml`,
`macros.yaml`, `auth/*`, `proxygroups.yaml`, `drules.yaml`,
`maintenance.yaml`, `dashboards/*`, `scripts/*` — это снимки вывода `*.get`,
не импортируемый формат. Их восстанавливают парными методами `*.create`
(или `*.update`), подавая в параметры содержимое YAML. Соответствие:

| Файл | Метод восстановления |
|---|---|
| `users/roles.yaml` | `role.create` |
| `users/usergroups.yaml` | `usergroup.create` |
| `users/users.yaml` | `user.create` |
| `alerting/actions.yaml` | `action.create` |
| `core/macros.yaml` | `usermacro.createglobal` |
| `auth/authentication.yaml` | `authentication.update` |
| `auth/userdirectories.yaml` | `userdirectory.create` |
| `proxygroups.yaml` | `proxygroup.create` |
| `drules.yaml` | `drule.create` |
| `maintenance.yaml` | `maintenance.create` |
| `dashboards/*.yaml` | `dashboard.create` |
| `scripts/*.yaml` | `script.create` |

Перед подачей удалите из payload поля, которые сервер присваивает сам
(`roleid`, `usrgrpid`, `userid`, и т.п.) и вспомогательные «резолвленные»
поля экспорта (`_role_name`, `_grp_name`, `_mt_name` — они добавлены для
читаемости и в `*.create` не нужны). Замените `[SECRET]` на реальные
значения из хранилища (раздел 6).

> **ID не сохраняются.** При пересоздании Zabbix выдаёт новые ID. Поэтому
> восстанавливать нужно по именам и в правильном порядке (раздел 2), а
> ссылки между объектами разрешать по именам, а не по старым ID.

## 5. Восстановление пользователей: локальные vs LDAP/SAML

- **Локальные пользователи** (`users/users.yaml`) пересоздаются через
  `user.create`. Пароли в выгрузке отсутствуют — задайте временные из
  хранилища/политики и потребуйте смены при первом входе.
- **LDAP/SAML-пользователи НЕ восстанавливаются как объекты** — они создаются
  заново автоматически (JIT provisioning) при первом входе, **если**
  корректно восстановлены: роли, группы пользователей, `auth/authentication.yaml`
  и `auth/userdirectories.yaml`. Маппинг групп для справки — в
  `auth/userdirectory_<имя>.csv` / `.md`.
- Поэтому порядок из раздела 2 (роли → группы → auth) обязателен: без него
  LDAP-вход поднимется, но пользователи получат неверные права или не увидят
  ничего.

## 6. Секреты (обязательное требование)

Выгрузки **не содержат** секретов — в полях стоит `[SECRET]` либо поля нет.
Восстановление без секретов поднимет структуру, но без рабочих паролей, PSK
и токенов мониторинг/оповещения работать не будут.

> **Требование:** организуйте источник секретов до аварии. Это может быть
> менеджер секретов (vault), защищённый парольный архив или документированный
> процесс. Сопоставление «объект → где лежит его секрет» должно
> поддерживаться отдельно от этого репозитория.

Перечень полей, требующих ручного ввода при восстановлении:

- **Локальные пользователи** — пароли (`user.create` → `passwd`).
- **Секретные макросы** (`core/macros.yaml`, `type: Secret`, значение
  `[SECRET]`) — реальные значения.
- **Прокси** (`infra/proxies/*`) — `tls_psk`, `tls_psk_identity`.
- **Типы оповещений / вебхуки** (`alerting/mediatypes.yaml`) — токены, пароли
  SMTP/API.
- **Скрипты** (`scripts/*`) — пароли для типов SSH/Telnet.
- **API-токены** — пересоздаются заново, в выгрузке отсутствуют.

После импорта пройдите по этому списку и подставьте значения через UI или
`*.update`.

## 7. Исторические данные метрик

Метрики (history/trends) **не входят** в git-выгрузки — это данные БД, не
конфигурация. Возможны два варианта, в зависимости от ваших требований:

**Вариант 1 — метрики критичны (есть бэкап БД).**
Восстановите БД Zabbix из бэкапа штатными средствами СУБД. Если БД
восстанавливается полностью — она содержит и конфигурацию, и метрики; тогда
git-выгрузки нужны лишь как сверка/частичный откат. Если из бэкапа берёте
только таблицы history/trends — сначала поднимите конфигурацию из git
(разделы 2–6), затем долейте исторические таблицы, согласовав ID объектов
(itemid и т.д.) — это нетривиально, т.к. при пересоздании конфигурации ID
меняются; реалистично только если конфигурация тоже из того же бэкапа БД.

**Вариант 2 — метрики некритичны.**
Восстановите только конфигурацию из git (разделы 2–6). Сбор метрик начнётся
заново с момента запуска; история до аварии будет отсутствовать. Для многих
инсталляций это приемлемо.

> Практический вывод: git-выгрузки — это быстрый и надёжный способ вернуть
> **рабочую конфигурацию**. Полное восстановление **с историей** требует
> бэкапа БД и согласованности ID, поэтому стратегию по метрикам определите
> заранее.

## 8. Проверка после восстановления (чек-лист)

- [ ] Группы хостов и шаблонов на месте, шаблоны привязаны.
- [ ] Хосты импортированы, интерфейсы/прокси заданы, статус не «не
      поддерживается» массово.
- [ ] Глобальные и секретные макросы заданы (секреты подставлены).
- [ ] Роли, группы пользователей и их права восстановлены.
- [ ] Локальные пользователи входят (пароли заданы).
- [ ] LDAP/SAML: тестовый вход создаёт пользователя с верными группами/ролью.
- [ ] Типы оповещений настроены, тестовое оповещение уходит (токены/пароли
      подставлены).
- [ ] Действия (триггерные/обнаружения) активны.
- [ ] Прокси на связи, хосты за прокси опрашиваются.
- [ ] Карты/дашборды/скрипты отображаются.
- [ ] Нет массовых ошибок в системных логах Zabbix server.
- [ ] (Если применимо) исторические данные доступны согласно выбранному
      варианту раздела 7.

## 9. После восстановления — вернуть синхронизацию в git

Когда инсталляция поднята и проверена:

1. Убедитесь, что Airflow Connections (`zabbix_<env>`, `gitlab_<env>`) и
   Variable (`<env>_gitlab_project_id` и пр.) указывают на восстановленный
   сервер.
2. Запустите вручную **полный** экспорт хостов
   `zabbix_core_full_to_gitlab_<env>` — он снимет актуальный снимок и
   подчистит осиротевшие файлы.
3. Прогоните остальные DAG (templates, auth, users, alerting, infra, ui),
   убедитесь в `errors=0`.
4. Дальше расписания продолжат поддерживать выгрузки в актуальном состоянии.

## Приложение. Карта репозитория

```
templates/                      шаблоны (configuration.export)
auth/
  authentication.yaml           настройки аутентификации (*.get)
  userdirectories.yaml          LDAP/SAML directories + provisioning (*.get)
  userdirectory_<имя>.csv|.md    маппинг групп (справочно)
users/
  roles.yaml  usergroups.yaml  users.yaml          (*.get → *.create)
alerting/
  mediatypes.yaml               (configuration.export)
  actions.yaml                  (*.get → action.create)
core/
  hostgroups.yaml  templategroups.yaml             (configuration.export)
  macros.yaml                   глобальные макросы (*.get)
  hosts/<имя>_<hostid>.yaml      хосты, по файлу на хост (configuration.export)
infra/
  proxies/<имя>.yaml             прокси (*.get)
  proxygroups.yaml  drules.yaml  maintenance.yaml   (*.get)
maps/<имя>.yaml                  карты (configuration.export)
dashboards/<имя>.yaml            дашборды (*.get)
scripts/<имя>.yaml               скрипты (*.get)
```

Формат файла: `configuration.export` — нативный импортируемый YAML Zabbix;
`*.get` — снимок вывода API (восстановление через парный `*.create`, см. 4.2).
